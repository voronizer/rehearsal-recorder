# Sets for a gig Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sets for a gig in the band service (lengths, total time, a stage view, a printed sheet), kept the same as РЭХА's sets both ways, with a **Check the band service** item beside **Start rehearsal**.

**Architecture:** The service gets two tables and a column (migration 0008), the band's set routes and РЭХА's set routes beside the songs' (`worker/sets/`), and a Sets section built from the mockup's components (`src/sets/`). РЭХА gets `service_set` (migration 0016) and `sending/service_sets.py`, which works as `service_songs.py` does (three values, push at once, check after the songs). The words and the site picture come last.

**Tech Stack:** Cloudflare Worker (Hono, zod-openapi, Drizzle, D1), React + TanStack Router/Query, РЭХА's shadcn components via `@/`; Python (SQLAlchemy, Alembic), pytest; Playwright; vitest.

**Spec:** `docs/superpowers/specs/2026-11-09-gig-sets-design.md`. Read it first; this plan argues from it.

## Global Constraints

- Writing rules in `CLAUDE.md`: British English, no AI tells, one word per thing (take, song, set, track, mark); button names in bold in the guide and CHANGELOG; curly quotes “ ” in the guide, site and CHANGELOG.
- Test titles and check labels: cp1252 characters only (no Cyrillic, no ♯ in test names).
- Set names: 1 to 40 characters, trimmed, unique among sets in use, compared case-blind (РЭХА's `LABEL_NAME_MAX = 40`).
- `typed_length`: whole seconds 1 to 3599, or null.
- Exact words: “There is already a set called {name}”, “Still in development”, “Check the band service”, “Nothing new in the band service.”, “The end”, “no takes”, “no length: {titles}”, the Delete set dialog: “It goes to the Trash, where anyone in the band can put it back for 30 days. Its songs stay as they are.”
- The service's `MIN_REHA_VERSION` does not change.
- While building, run only the tests a change touches, once each; full suites run once, on CI.
- Never commit `service/.mk-sets/` (the mockup's scratch copy). Its components are in `/mnt/project-files/band-service/sets/mock-src/` to start from.

## Review Focus

1. A song in a set is deleted in the service: the set hides it there, РЭХА drops its title from its sets when it removes the song, and the next push does not make the song again (Task 3 test `test_song_deleted_in_service_leaves_sets`).
2. One name given on both sides before a check. A set made in РЭХА with a name the service has becomes that set, with РЭХА's songs (`POST` answers its id). A set renamed in РЭХА to a name another set has there gets 409, and РЭХА renames its own to “{name} 2” and sends that; nothing loops (Task 3 test `test_same_name_both_sides_gets_2`, Task 1 test `reha: a set made in reha with a name the service has is that set`).
3. Typed lengths: “4:05” and “12:30” are kept; “4:5”, “4:65”, “abc” and “-1:00” are not, the field stays open and red; an empty field goes back to the best take's (Task 2 unit test for `parseLength`).
4. **On stage** with an empty set is disabled; on the last song › reads “The end” and is disabled; a swipe past either end does nothing (Task 2 e2e).
5. Two songs merged in РЭХА when both are in one set: the service's merge keeps the target in its place and drops the merged one; when only the merged one is in the set, the target takes its place (Task 1 test).

### Task 1: The service's sets: storage and routes

**Files:**
- Modify: `service/worker/shared/schema.ts` (tables `bandSet`, `setSong`, column `song.typedLength`)
- Create: `service/migrations/0008_sets.sql` with `npx drizzle-kit generate --name sets` (journal and snapshot with it)
- Create: `service/worker/sets/store.ts`, `service/worker/sets/routes.ts`, `service/worker/sets/reha-routes.ts`
- Modify: `service/worker/index.ts` (mount both), `service/worker/songs/routes.ts` (`typed_length` in `SongItem` and `PATCH /api/songs/{id}`), `service/worker/songs/sync.ts` (`mergeSong` moves set places), `service/worker/takes/band-routes.ts` (`/api/trash` lists sets; `POST /api/trash/sets/{id}/restore`), `service/worker/takes/purge.ts` (sets 30 days in the Trash go for good)
- Modify: `service/openapi.json` via `npm run openapi`
- Test: `service/test/sets.test.ts` (new)

**Interfaces:**
- Produces, for the band (cookie): `GET /api/sets` → `{ sets: { id: number; name: string; songs: number[] }[] }` in list order, songs in the Trash left out; `POST /api/sets {name}` → `{ id }`; `PATCH /api/sets/{id} {name?, songs?}` → `{ ok: true }`; `DELETE /api/sets/{id}` → `{ ok: true }`; `POST /api/trash/sets/{id}/restore` → `{ ok: true }`; `GET /api/trash` gains `sets: { id, name, songs: number, trashed_at, by }[]`; `SongItem.typed_length: number | null`; `PATCH /api/songs/{id}` takes `typed_length`.
- Produces, for РЭХА (key): `POST /api/reha/sets/link {sets: {name, songs}[]}` → `{ ids: number[] }`; `POST /api/reha/sets {name, songs}` → `{ id }`; `PATCH /api/reha/sets/{id} {name?, songs?}` → `{ ok: true }`; `DELETE /api/reha/sets/{id}` → `{ ok: true }` (404 when no such set); `GET /api/reha/sets` → `{ sets: { id, name, songs: number[], trashed: boolean, made_by: string|null, changed_by: string|null, trashed_by: string|null }[] }` (names, not user ids; songs in the Trash left out).
- Errors: 400 bad body or a song number the service does not have (“No such song: 12”), 404 “No such set”, 409 “There is already a set called {name}” on a name clash (band PATCH, РЭХА PATCH, Restore).

**Interfaces:**
- Consumes: Task 1's РЭХА routes and `service/openapi.json`.
- Produces: `ServiceClient.link_sets(sets) -> list[int]`, `add_set(name, songs) -> int`, `change_set(sid, **fields)`, `delete_set(sid)`, `sets() -> dict` (refuses an answer not in shape); `ServiceSets(service)` with `forget()`, `owed()`, `push(client)`, `check(client) -> int` (changes brought); `Api.check_band_service() -> {"ok": True}`.

Rules, from the spec: three values per set (name, and songs as service numbers); РЭХА's own change goes after the songs, before any take; a title that is no song is made a song first (`Library.add_song`); at the check a name taken here gets “ 2” (the free-name rule of `SetsSettings.tsx` `freeName`); a 409 on PATCH renames РЭХА's set the same way and sends again; a set deleted in РЭХА keeps its `service_set` row with `set_id` null until `DELETE` is answered (404 counts as done); `forget_service` forgets the rows. The button calls `BandService.check_soon(manual=True)`; a manual check that brought nothing gives the notice “Nothing new in the band service.”
